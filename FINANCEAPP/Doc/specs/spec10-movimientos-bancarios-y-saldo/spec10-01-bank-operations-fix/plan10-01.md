## 1. Enfoque

Se respeta el patrón página `.razor` → `IBankService` → `AppDbContext`. Toda la lógica (signo, validación, redondeo y saldo) va en `BankService`; las páginas recogen datos y muestran mensajes.

La causa del fallo es que `CreateOperationAsync`, `UpdateOperationAsync` y `DeleteOperationAsync` abren una transacción y llaman a `RecalculateAccountBalanceAsync`, que abre otra (SQLite no admite anidadas). La solución es que `RecalculateAccountBalanceAsync` **no abra transacción propia** y se llame solo desde dentro de las transacciones ya abiertas, como `PropertyService.RecalculatePropertyTotalsAsync`. Si alguien lo llama suelto, su único `SaveChangesAsync` ya es atómico.

El esquema evoluciona solo con `DatabaseSchemaUpgrader`: columna nueva `OpeningBalance`, sin perder datos y sin migraciones de EF.

## 2. Modelo de datos

`BankAccount` gana un campo:

| Campo | Significado |
|---|---|
| `OpeningBalance` (`decimal(18,2)`, por defecto 0) | Saldo previo a los movimientos registrados. `CurrentBalance` = `OpeningBalance` + efecto de los movimientos. |

El efecto de un movimiento es `+|Amount|` para Ingreso, Intereses y Traspaso Entrada, `−|Amount|` para Gasto, Comisiones y Traspaso Salida, y 0 para cualquier otro tipo. No cambia `BankOperation`.

Migración para BD existente (`EnsureBankAccountOpeningBalanceColumn`), solo cuando la columna **no existe**:
1. `ALTER TABLE BankAccounts ADD COLUMN OpeningBalance decimal(18,2) NOT NULL DEFAULT 0`.
2. Para cada cuenta: `OpeningBalance = CurrentBalance − efecto de sus movimientos` (SQL con `CASE` sobre `Type` y `ABS(Amount)`, agrupado por `AccountName`).
Así el saldo mostrado no cambia y, al repetir el arranque, la columna ya existe y no se vuelve a calcular. Las cuentas sin movimientos quedan con `OpeningBalance = CurrentBalance`.

## 3. Algoritmos (`BankService`)

### 3.1 Utilidades privadas
- `GetSignedAmount(type, amount)`: `Math.Round(Math.Abs(amount), 2, MidpointRounding.AwayFromZero)`, con signo negativo si el tipo es de gasto; 0 si el tipo no es válido.
- `ValidateOperation(operation)`: lanza `InvalidOperationException` con mensaje en español si el tipo no está en la lista de seis, el importe es ≤ 0 (se comprueba `Math.Abs` solo en filas ya guardadas; en la entrada se exige > 0), supera 999.999.999,99, la fecha es `default` o la descripción pasa de 500 caracteres.

### 3.2 `CreateOperationAsync`
1. Validar (3.1).
2. Abrir transacción; buscar la cuenta o lanzar «No existe cuenta llamada…».
3. Normalizar `Amount = GetSignedAmount(...)`, `Description` recortada; añadir y guardar.
4. `RecalculateAccountBalanceAsync(accountName)` (sin transacción propia); confirmar. Si algo falla, revertir.

### 3.3 `UpdateOperationAsync`
1. Validar; abrir transacción; cargar la operación o lanzar «No existe operación…».
2. Rechazar un cambio de `AccountName` (fuera de alcance): mantener el original.
3. Actualizar tipo, importe normalizado, fecha y descripción; guardar; recalcular la cuenta; confirmar.

### 3.4 `DeleteOperationAsync`
Igual que hoy, pero el recálculo ya no abre transacción anidada.

### 3.5 `RecalculateAccountBalanceAsync`
1. Cuenta por nombre (o error).
2. `CurrentBalance = OpeningBalance + Σ efecto` (usando `Math.Abs` y el tipo).
3. `UpdatedAt = DateTime.Now`; un único `SaveChangesAsync`. Sin `BeginTransactionAsync`.

### 3.6 Cuentas
- `CreateBankAccountAsync`: `OpeningBalance = CurrentBalance`.
- `UpdateBankAccountAsync`: tras copiar los campos, `OpeningBalance = CurrentBalance − Σ efecto de sus movimientos` (así el saldo escrito a mano es el que se ve). Si cambia el nombre, los movimientos siguen ligados al nombre antiguo (regla conocida del proyecto): se calcula con el nombre original.
- `DeleteBankAccountAsync` no cambia.

## 4. Interfaz

### 4.1 `BankOperationsList.razor`
- Estado: `newOperation` (fecha inicial `DateTime.Today`), `editingId` (`int?`), `message` y `messageIsError`, `isSaving`.
- «Añadir»/«Guardar cambios» llama al servicio dentro de `try/catch`: muestra `InvalidOperationException.Message` tal cual; para cualquier otra excepción, un mensaje genérico en español y registro en el log. El botón se desactiva con `isSaving` (evita el doble clic).
- Fila: nuevo botón «Editar» (`editingId = op.Id`, copia a `newOperation` con `Math.Abs(Amount)`); «Eliminar» desactivado en la fila que se edita y con `confirm` de JS (`IJSRuntime` inyectado, como en `BankAccountsList`).
- «Cancelar» limpia el modo edición. Título del formulario: «Nueva operación» o «Editar operación».
- Quitar la validación duplicada (`Type`/`Amount`) del `AddOperation` actual.
- Alerta de éxito/error bajo el formulario.

### 4.2 `BankAccountsList.razor`
- `RefreshAccounts` deja de poner `isLoading = true` salvo en la primera carga (`OnInitializedAsync`), para no destruir el desplegable.

## 7. Casos límite

- BD existente con movimientos: el saldo mostrado no cambia tras la migración.
- Fila antigua de Gasto con importe positivo: el efecto usa valor absoluto y el tipo; el saldo ya se calcula bien, y la fila se normaliza si se edita.
- Cuenta sin movimientos y con saldo manual: `OpeningBalance` = saldo.
- Cambiar el nombre de una cuenta: sus movimientos quedan ligados al nombre antiguo (regla del proyecto); el saldo se calcula con el nombre original al guardar la cuenta.
- Tipos desconocidos en filas antiguas: efecto 0.
- Fallo a mitad de la transacción: se revierte entera.
