> Al deshacer un registro del histórico de ventas se reabren las compras que cerró y se elimina la venta.

## 1. Contexto y objetivo

Hoy, al eliminar un registro de `/sales-history`, las compras que esa venta cerró **siguen cerradas** (SPEC-02-01 lo documenta como limitación: «borrar no reabre»). El resultado es que las acciones y el total invertido de la empresa quedan mal tras deshacer una venta.

Petición original:

> me he fijado al deshacer un histórico de ventas no me ha vuelto a abrir las compras vinculadas que habia cerradas, quiero que cuando las cierre, crear un campo nuevo en las operaciones financieras con el id venta informado con el id del histórico de venta que lo ha cerrado y cuando haga el deshacer venta limpie ese id, quite la fecha de cierre y vuelva a dejar esas compras como abiertas

Objetivo: que cada compra cerrada por una venta guarde el Id del registro de histórico que la cerró, y que al deshacer esa venta se limpie el Id, se quite la fecha de cierre y la compra vuelva a estar abierta, dejando la posición de la empresa como antes de vender.

## 2. Usuarios

Un único usuario: el propietario de la aplicación, que registra sus operaciones de acciones y consulta el histórico de ventas.

## 3. Historias de usuario

- Como inversor, quiero que cada compra cerrada recuerde qué venta la cerró, para poder saber de dónde viene su cierre.
- Como inversor, quiero deshacer una venta desde el histórico y que sus compras vuelvan a estar abiertas, para corregir una venta mal registrada sin perder mis posiciones.
- Como inversor, quiero que las compras que se partieron en dos al vender vuelvan a ser una sola fila al deshacer, para no acumular filas duplicadas.

## 4. Requisitos funcionales

### RF-1 · Campo `SaleHistoryId` en las operaciones

`Operation` incorpora un campo opcional `SaleHistoryId` (entero nulo) con el Id del registro de `SalesHistory` que cerró la operación. Vacío en operaciones abiertas y en las cerradas por otros medios.

- [ ] La tabla `Operations` de una BD ya existente gana la columna `SaleHistoryId` (nula) sin perder datos, desde `DatabaseSchemaUpgrader`.
- [ ] Las operaciones existentes quedan con `SaleHistoryId` vacío.

### RF-2 · Informar el Id al cerrar compras

Al registrar una Venta nueva (`RegisterSaleAsync`), cada compra o traspaso que se cierra (completo, o la parte cerrada de un lote partido) guarda el Id del registro de histórico creado.

- [ ] Tras una venta total, todas las compras cerradas tienen `SaleHistoryId` = Id del nuevo registro.
- [ ] Tras una venta parcial, la fila cerrada tiene el Id y la fila abierta pendiente lo tiene vacío.
- [ ] Una venta rechazada por acciones insuficientes no deja ningún Id escrito.
- [ ] Todo ocurre en la misma transacción que el cierre y el alta del histórico.

### RF-3 · Vínculo entre las filas de un lote partido

Para poder volver a unirlas, las filas que salen de partir un lote comparten un identificador de origen (`OriginOperationId`: Id de la fila original del lote, que conserva su Id). Se informa en la fila cerrada y en la pendiente al partir; si la pendiente se vuelve a partir en otra venta, las nuevas filas heredan el mismo origen.

- [ ] Al partir un lote, las dos filas comparten `OriginOperationId`.
- [ ] Al volver a partir una fila pendiente, las filas nuevas heredan el origen del lote inicial.
- [ ] Las compras que no se parten tienen `OriginOperationId` vacío.

### RF-4 · Deshacer venta

Desde `/sales-history`, la acción sobre un registro pasa a **deshacer la venta** (decisión de la sección 6). En una sola transacción:

1. Las compras y traspasos con `SaleHistoryId` = Id del registro quedan con `SaleHistoryId` vacío y `CloseDate` vacía (abiertas).
2. Si alguna de esas filas procede de un lote partido (`OriginOperationId`), se une con las demás filas **abiertas** del mismo origen que coincidan en tipo, fecha y precio por acción: se queda la de menor Id con la suma de acciones, importes y comisiones, y se borran las demás.
3. Se elimina la operación de tipo Venta que originó el registro (`OperationId`).
4. Se elimina el registro del histórico.
5. Se recalcula la empresa (`RecalculateTotalInvestedAsync`).

- [ ] Tras deshacer una venta total, sus compras vuelven a estar abiertas, sin `SaleHistoryId` y sin fecha de cierre.
- [ ] Tras deshacer una venta parcial, la compra cerrada y su parte pendiente se unen en una sola fila con las acciones, el importe y la comisión originales (sin perder céntimos).
- [ ] La operación Venta y el registro del histórico desaparecen.
- [ ] En `/companies`, acciones y total invertido de la empresa coinciden con los de antes de vender.
- [ ] Si algo falla, no se cambia nada (transacción con reversión).
- [ ] Se puede deshacer cualquier venta aunque existan ventas posteriores de la misma empresa; solo se reabren las compras con el Id de esa venta y no se tocan las de otras.
- [ ] El deshacer no está sujeto al bloqueo de RF-6 (es la única vía para tocar esas operaciones).
- [ ] Si el registro no tiene compras vinculadas (venta anterior a la feature), se eliminan la Venta y el registro sin reabrir nada y la pantalla lo avisa.
- [ ] Si el registro ya no existe, se muestra «El registro ya no existe» y el listado se refresca sin cambios.

### RF-5 · Aviso en pantalla

El botón de la fila de `/sales-history` pasa de «Eliminar» a «Deshacer venta» (icono de deshacer) y su modal de confirmación explica que la venta se deshace: se reabren las compras, se unen las filas partidas y se elimina la venta y su registro.

- [ ] El botón se llama «Deshacer venta» y la edición del precio de venta no cambia.
- [ ] El modal ya no dice que las compras «no se reabren».
- [ ] Tras confirmar, el listado se refresca sin el registro y los errores se muestran en pantalla.

### RF-6 · Bloqueo de operaciones cerradas por una venta

Desde `/operations` no se pueden **editar ni eliminar** las operaciones cerradas por una venta: las compras y traspasos con `SaleHistoryId` y las Ventas que tienen registro en el histórico (`SalesHistory.OperationId`). Al intentarlo, no se abre la edición ni se borra y se muestra un mensaje que indica ir a `/sales-history` y deshacer la venta. El bloqueo se aplica en el servicio (`UpdateAsync` y `DeleteAsync`) y la página lo muestra.

- [ ] Editar o eliminar una compra o traspaso con `SaleHistoryId` muestra el mensaje y no cambia nada.
- [ ] Editar o eliminar una Venta con registro en el histórico muestra el mismo mensaje y no cambia nada.
- [ ] Las compras abiertas (incluida la parte pendiente de un lote partido), las Ventas antiguas abiertas, los dividendos y las operaciones cerradas a mano (sin `SaleHistoryId`) siguen siendo editables y eliminables.
- [ ] Tras deshacer la venta, sus compras vuelven a ser editables y eliminables.
- [ ] El bloqueo no afecta al borrado en cascada de una empresa (`CompanyService`).

## 5. Requisitos no funcionales

- **Datos**: columnas nuevas solo desde `DatabaseSchemaUpgrader` (comprobación `PRAGMA table_info`, nulas, sin borrar ni recrear nada). Backup previo y pruebas sobre copia de la BD.
- **Arquitectura**: la lógica va en `OperationService` (tiene acceso a la empresa); la página solo llama al servicio. SQLite no admite transacciones anidadas: el recálculo se llama dentro de la transacción abierta.
- **Idioma**: textos y mensajes en español; identificadores en inglés. Ficheros con CRLF.
- **Compatibilidad**: sin paquetes nuevos; las ventas y compras anteriores a la feature siguen funcionando.

## 6. Decisiones cerradas con el usuario

1. **Operación Venta**: al deshacer, se **borra** (junto con el registro del histórico), como si la venta no hubiera existido.
2. **Compras divididas**: al deshacer, se **vuelven a unir en una sola fila**. Requiere el vínculo de RF-3.
3. **Orden**: se puede deshacer una venta antigua aunque haya ventas posteriores de la empresa.
4. **Operaciones cerradas por una venta** (compras, traspasos y Ventas del histórico): **no se pueden editar ni borrar** desde `/operations`; el mensaje remite al histórico, donde se deshace la venta (sustituye a la decisión previa «borrar una Venta queda como hoy»).
5. **Segundo campo `OriginOperationId`** aprobado para volver a unir los lotes partidos.
6. **Ventas ya registradas** antes de la feature: no se hace nada desde la app ni desde esta feature; el usuario las eliminará a mano. Sin limpieza automática de datos (constitución, principio 5).
7. **Resoluciones menores acordadas**: la Venta no lleva `SaleHistoryId` (se localiza por `OperationId`); se recalculan las empresas de las compras reabiertas y la del registro, sin duplicar; el botón pasa a «Deshacer venta».

## 7. Casos límite

- Compra cerrada **borrada** a mano después de la venta: no se encuentra, se ignora; el resto se reabre.
- Operación Venta ya borrada desde `/operations`: el registro se deshace igualmente y no falla.
- Compra con el mismo origen pero editada (tipo, fecha o precio distintos): se reabre pero no se une.
- Lote partido cuyas filas hermanas siguen cerradas por otras ventas: solo se unen las abiertas.
- Registro de ventas anteriores a esta feature (sin compras con `SaleHistoryId`): se eliminan la Venta y el registro, no se reabre nada y se avisa; el usuario las limpiará a mano.
- Empresa renombrada tras la venta: se recalculan el nombre actual de las compras reabiertas y el del registro, sin repetir.
- Registro inexistente (doble pulsación o borrado previo): mensaje «El registro ya no existe» y listado refrescado.
- Compra cerrada **editada** a mano antes de esta feature de bloqueo o por otra vía: se reabre igualmente si conserva el Id.
- Compra abierta con `OriginOperationId` editada por el usuario (acciones, importe o comisión): al unir se suman los valores actuales.

## 8. Fuera de alcance

- Que borrar una Venta desde `/operations` deshaga la venta (queda bloqueado, RF-6).
- Limpiar o migrar las ventas registradas antes de esta feature: las elimina el usuario a mano.
- Generar el vínculo retroactivo en ventas anteriores a la feature.
- Recalcular los beneficios guardados de otras ventas.
- Mostrar en `/operations` qué venta cerró cada compra.
